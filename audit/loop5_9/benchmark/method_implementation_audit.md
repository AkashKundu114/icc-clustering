# Benchmark method implementation audit

## Evidence scope

Inspected the local FYP source at HEAD `60b163f22b5931da35a1ace07d1934bf3bdd65e3` and historical producer/configuration sources at commits `7f74f6842ae02bc8fd9203fab18a56b7c68035c` and `567c5260972f1ce29124ce8449a907bebe8b3983`. Inspected saved Pass F and CoHiRF CSVs, dataset registry/loaders, `configs/baselines.yaml`, method implementations under `src/icc/baselines/`, `consensus_v2.py`, Pass F merge scripts and benchmark reports. The audit script `audit/loop5_9/benchmark/audit_benchmark.py` was executed and independently reconstructed the 2,750-row Pass F matrix from `high_d_30seeds_all_models.csv` plus the seven non-high-D rows from Pass E; all identifiers and scores matched, with floats compared at 1e-12 tolerance. It did not rerun clustering.

## What the saved benchmark is

The 13×12 benchmark consists of two artifact families, not one seed-paired factorial run:

- Pass F: 2,750 saved ARI/NMI/runtime observations, 11 named methods. Historical `scripts/compute_passF_stats.py` merges 1,980 high-D rows with 770 Pass E non-high-D rows.
- CoHiRF: 250 saved score rows in a separate file, using seeds 42–71 on the six high-D sets and 42–51 on seven others.
- Combined: 3,000 rows, 156 dataset×method cells, 30 rows per cell on six high-D data sets and 10 on seven others; no duplicate `(dataset, method, seed)` keys.

The merge chain is partly recoverable from the historical source tree. For high-D data, Pass F seeds 0–9 come from Pass E; seeds 10–29 for eight fast methods and DEC are produced by named Pass F scripts; ICC-v2 seeds 10–29 are copied from a separate Pass E ARI file; Ward seeds 10–29 are copied from Ward seed 0. The 7 non-high-D datasets use Pass E rows for 10 seeds. Thus 3,000 is a row/score-observation count, not evidence of 3,000 fresh, independently executed model fits. At minimum, the 120 high-D Ward rows at seeds 10–29 are duplicated scores generated by a merge script, not distinct runs. ICC-v2's imported rows may represent prior fits, but that separate file contains ARI only and has no individual run manifest here.

## Dataset and label handling

The broad matrix runner loads each dataset with the configured preprocessing and passes `K = len(unique(y))` (or loader metadata derived from `y`) to all methods. Therefore the number of clusters is externally supplied from reference labels, not estimated unsupervised. The same loaded matrix and K are provided to methods within each dataset, but this is a supervised choice of K and must be stated. ARI/NMI use `y` only after predictions, except dataset construction/preprocessing can use label-derived sample masks in particular loaders (for example, Indian Pines removes background pixels based on `ground_truth > 0`).

Most loaders impute missing feature values and standardize using all samples before clustering; Newsgroups constructs TF-IDF over the full corpus; Zheng68K uses the reduced Scanpy PBMC subset and stored label annotations. The repository does not attach stable sample IDs or input-cache SHA-256 to benchmark rows. No train/test split is used for these transductive clustering scores. These scores should not be described as held-out generalization.

## Method-by-method configuration/fairness findings

The machine-readable implementation/fairness table is `fairness_matrix.csv`. Key source findings:

- K-Means uses the shared `run_clusterer` wrapper with random initialization and `n_init=1`; this is lower initialization effort than some other implementations.
- Ward adds seed-controlled Gaussian jitter before hierarchical Ward. Contrary to the merge-script comment that Ward is deterministic, its wrapper is seed-dependent; Pass F copies the seed-0 score into seeds 10–29, masking that sensitivity.
- Spectral uses a 10-nearest-neighbor affinity and seeded KMeans label assignment. FCM uses the repository's own FCM-like implementation. They are not identical geometries/compute budgets to K-Means or Ward.
- Standard Consensus and Core-Halo/Li use 25 KMeans base partitions; ICC-v1 also uses 25 base partitions. These methods have substantially more internal fits than one-fit baselines. ICC-v2 uses 25 internal partitions, a 40-anchor cap, 15% candidate pool and, by default, a base engine selected by sample count (Spectral when N≤100; K-Means otherwise). The small biomedical cohorts therefore use a different base engine from Standard Consensus. This complicates attribution of differences to the ICC consensus alone.
- DEC is a custom deep clustering implementation, with a neural autoencoder, default 200 pretraining and up to 100 fine-tuning epochs; runtime/backend can vary by available hardware. It is not compute matched to the classical methods.
- FCAG and FastMVC are internal implementations, not independently validated against official reference packages here. The code explicitly labels FastMVC as **FastMVC-Surrogate**, an internal proxy, not faithful official FastMVC/FastMICE. The benchmark CSV and figures call it `FastMVC`; those results must not be attributed to the published FastMVC method.
- CoHiRF is implemented locally with `repetitions=25`, subspace fraction 0.15 and consensus threshold 0.80. Its 42-based seeds differ from the Pass F methods; equal repeat counts do not mean paired random experiments.

No method-tuning logs, matched wall-clock/compute budget protocol, or implementation-parity tests were found in the examined source. Method-specific defaults are not automatically unfair, but without an explicit comparison objective and tuning budget the results are descriptive performance comparisons of these particular implementations, not definitive ranking of published algorithms.

## Failure handling and missing status

Pass F's historical run scripts catch exceptions for several methods and encode ARI/NMI as 0.0; the output rows have no `status`, exception message or traceback. The broad benchmark matrix likewise contains no fit-status field. Saved Pass F contains 42 Core-Halo rows with both ARI and NMI exactly zero (12 CNS, 30 Prostate), among other zero ARIs; these cannot be distinguished from valid chance/degenerate predictions using the CSV. Runtime is nonzero for all rows and does not disambiguate catches in the seed-extension scripts, which record elapsed time even on error. This is a material ambiguity for means/ranks, especially for Core-Halo. Do not silently treat every zero as a successful output or as a failure.

CoHiRF's helper does not catch a model exception and does not save failure-status records; complete row counts show output completeness only, not absence of crashes/retries or correct execution.

## Determination

Source/configuration inspection verifies the saved score table's *assembly* and makes several design choices visible. It does not establish historical fit execution. The broad score comparison is suitable only as a descriptive benchmark under the saved implementations/configurations, with externally supplied K, nonpaired method seeds, copied Ward scores, imported ICC-v2 scores, potentially imputed failures, and an explicitly surrogate FastMVC baseline. No universal ICC-v2 superiority, robustness, or generalization claim is supported by this benchmark audit. A Friedman rank position is not a superiority conclusion.

No source, configuration, result CSV or manuscript was modified. No benchmark fit was executed in this audit.
